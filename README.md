# QE AI Portfolio

The project contains independently runnable QE tools plus an orchestrator that runs a configured subset and combines their findings.

For the non-AI Playwright workflows (UI, API, accessibility, visual, database, and Pact), see [README.testing.md](./README.testing.md).

| Capability | Main value |
|---|---|
| Failure analysis and triage | Explains individual test failures |
| Cross-run failure intelligence | Detects recurring or intermittent failures |
| Release readiness quality gate | Evaluates requirement coverage and release risk |
| AI test design and test-to-code | Turns requirements into scenarios and candidate Playwright tests |
| Test impact analysis | Selects mapped tests affected by code changes |
| API contract intelligence | Detects structural API contract changes |
| Test data intelligence | Checks data quality and scenario coverage; creates synthetic data |
| Performance intelligence | Identifies threshold breaches and performance regressions |
| AI agent evaluation | Regression-tests AI responses against expected behaviors |
| QE intelligence orchestrator | Runs enabled agents and consolidates their findings |

These tools exchange structured JSON reports where possible. AI recommendations use local Ollama by default; deterministic checks provide the measurable findings, while AI output is advisory.

# Utilities and QE Workflow

This guide explains the TypeScript tools in `utils/` (excluding `db.ts`) and how their inputs and outputs fit together.

## At a glance

- **Design tests:** Requirements Markdown → `qe-test-design-agent.ts` → scenario JSON and Markdown.
- **Generate test candidates:** Scenario JSON → `qe-test-to-code.ts` → candidate Playwright specs.
- **Analyze failures:** Playwright JSON → failure agent or AI analysis, with `qe-failure-triage.ts` providing reusable rule-based triage.
- **Track patterns across runs:** Playwright JSON → `qe-run-history.ts` → JSONL history → `qe-failure-intelligence.ts` → cross-run report.
- **Check release readiness:** Requirements, scenarios, test results, risk configuration, and failure intelligence → `qe-quality-gate.ts` → readiness decision and reports.

The AI-powered tools use a local Ollama server by default (`http://localhost:11434`, model `qwen3:4b`). AI-generated scenarios and tests are candidates for human review, not proof of correctness.

## Copilot project instructions and prompts

Workspace guidance lives under `.github/`: `copilot-instructions.md` provides concise project-wide rules, while `.github/instructions/` adds Playwright, Pact, and QE-specific guidance when the related files are in scope. Reusable task prompts are in `.github/prompts/`.

Fill in the requested scenario, failure evidence, or agent change; review the proposed edits and validation before accepting them. These customizations guide Copilot but do not replace human review or execute tests automatically.

## MCP connection for QE reports

The project includes a small **read-only MCP server** at `mcp/qe-mcp-server.ts`. It connects an MCP client such as VS Code Copilot to existing QE reports; it is not a test runner or another AI agent.

- `.vscode/mcp.json` starts the QE report server over **stdio** using the project's local Node.js and `tsx` dependencies, and adds GitHub's hosted MCP server over HTTP.
- Sign in to GitHub when VS Code prompts; the GitHub tools and data available depend on your account and repository permissions.
- `list_qe_reports` shows which known reports exist and when they were last modified. `get_qe_report_summary` returns a concise summary for release readiness, unified QE, test impact, API contracts, test data, performance, or AI evaluation.
- To try it, run `npm ci`, open the workspace in VS Code, start/trust `qe-report-server` from the MCP server controls, then ask Copilot: “List the QE reports” or “Summarize the release-readiness report.”
- Reports must be generated by their normal QE scripts first; this MCP server does **not** run tests, invoke Ollama, modify files, access arbitrary paths, or connect to a database.
- The server uses fixed report names and paths and returns selected summaries rather than entire report contents. Only start MCP servers you trust; this one runs as a local process with the current user's filesystem permissions.
- GitHub is a separate external service; review tool permissions and approval prompts before using actions that could change issues, pull requests, or repository content. No GitHub token is stored in this workspace configuration.

## Additional QE Agents

These agents live in their own folders, separate from the core scripts under `utils/`. Their default inputs and reports are inside their respective folders.

### Test Data Intelligence — `ai-test-data-management-agent/`

- Reads `test-data/schema.json`, `test-data/source-data.json`, and `test-data/scenarios.json` to understand field rules, example records, and data scenarios.
- Validates required fields, types, formats, ranges, allowed values, and uniqueness; also flags fields that may contain sensitive data.
- Checks whether the sample records provide data for each scenario, such as a missing value, duplicate, or boundary value.
- Generates 20 synthetic customer records using schema metadata, rather than copying the source records.
- Uses local Ollama for additional recommendations; deterministic findings remain available if AI recommendations are unavailable.
- Writes `test-results/qe-test-data-intelligence.json`, `test-results/qe-test-data-intelligence.md`, and `test-results/generated-synthetic-customers.json`.
- **Why use it:** Find gaps in test data before execution and produce safer synthetic records for non-production testing.
- **Run:** `npm run qe:test-data`.
- **Prerequisite / flow:** Update the three input JSON files first; generated synthetic records and reports are outputs for human review or downstream use.

### Test Impact Analysis — `ai-test-impact-analysis-agent/`

- Gets changed files from Git by comparing `QE_BASE_REF` (default `origin/main`) with `HEAD`, then adds staged, unstaged, and untracked changes.
- Matches changed source files against `test-data/test-impact-map.json`; changed Playwright spec files are selected directly.
- Checks that mapped test files exist and flags changed source files without a mapping.
- Recommends `RUN_SELECTED_TESTS` only when mappings are sufficient; otherwise it recommends `FULL_SUITE_REQUIRED`.
- Adds a local Ollama explanation, but the selected tests and recommendation are determined by the mapping and change evidence.
- Writes `test-results/qe-impact-report.json`, `test-results/qe-impact-report.md`, and `test-results/qe-selected-tests.txt`.
- **Why use it:** Focus regression runs on tests associated with a change, while surfacing gaps that mean a targeted run may not be safe.
- **Run:** `npm run qe:impact`; set `QE_BASE_REF` if the comparison branch is not `origin/main`.
- **Prerequisite / flow:** Run in a Git checkout with the comparison ref available and keep the impact map current; missing mappings trigger a full-suite recommendation.

### API Contract Intelligence — `api-contract-analysis-agent/`

- Compares `api-contracts/baseline/openapi.json` with `api-contracts/current/openapi.json` and uses `api-contracts/api-test-map.json` to link operations to tests and requirements.
- Deterministically checks for removed endpoints, response/request schema changes, required-field changes, and removed successful response codes.
- Maps detected operation changes to impacted test files and reports missing test files or unmapped operations.
- Uses local Ollama to explain the detected changes; the AI explanation does not override the structural comparison.
- Writes `test-results/qe-api-contract-report.json` and `test-results/qe-api-contract-report.md`, including a review recommendation.
- **Why use it:** Identify possible consumer-impacting API changes and the tests to run before a contract change ships.
- **Run:** `npm run qe:api-contract`.
- **Prerequisite / flow:** Update both OpenAPI files and the operation-to-test map for the same API version change before comparing.

### Performance Engineering Intelligence — `perf-eng-intelligence-agent/`

- Reads current k6 metrics from `test-data/qe-performance/current/k6-summary.json`, an optional baseline from `baseline/k6-summary.json`, and JMeter CSV results from `current/jmeter-results.csv`.
- Uses `test-data/qe-performance/thresholds.json` to check response-time, error-rate, throughput, endpoint, and baseline-regression limits.
- Calculates deterministic findings and a release-risk label, then asks local Ollama for engineering recommendations.
- Requires at least one current k6 or JMeter result; baseline comparison is included when configured and a baseline file is available.
- Writes `test-results/qe-performance-intelligence.json` and `test-results/qe-performance-intelligence.md`.
- **Why use it:** Turn load-test output into threshold-based regression signals and an actionable performance summary.
- **Run:** `npm run qe:performance`.
- **Prerequisite / flow:** Run k6 and/or JMeter first and place their results in the input folders; adjust thresholds to match service objectives.

### QE AI Agent Evaluation — `qe-ai-agent-evaluation/`

- Reads evaluation cases from `test-data/qe-ai-evals/cases.json`; each case supplies evidence, a question, expected facts, and required or forbidden phrases.
- Sends each prompt to the configured Ollama model and checks responses with deterministic assertions, including whether embedded prompt-injection text is ignored.
- Records per-case checks, scores, model latency, and errors; compares the overall pass rate with the configured threshold.
- Writes `test-results/qe-ai-evaluation/qe-ai-evaluation-report.json` and `test-results/qe-ai-evaluation/qe-ai-evaluation-report.md`.
- Exits with failure when the pass-rate gate is below `passRateThreshold`; the cases and checks are a regression signal, not proof that the model cannot hallucinate or be attacked.
- **Why use it:** Catch regressions in the AI agent's grounding, uncertainty handling, and resistance to instructions embedded in evidence.
- **Run:** `npm run qe:ai-eval`.
- **Prerequisite / flow:** Ollama and its configured model must be running; edit `cases.json` to define behaviors and `passRateThreshold` to set the gate.

### QE Intelligence Orchestrator — `qe-intelligence-orchestrator/`

- Reads `test-data/qe-orchestrator/config.json` to decide which npm scripts to run, which agents are required, and which JSON reports to collect.
- Runs enabled agents sequentially, captures their console output in `test-results/qe-orchestrator/logs/`, and removes each configured old report before its agent runs to avoid using stale results.
- Parses available reports, normalizes findings and severities, and combines them with agent failures and gate decisions into a heuristic risk score.
- Writes `test-results/qe-orchestrator/qe-unified-intelligence-report.json` and `test-results/qe-orchestrator/qe-unified-intelligence-report.md`.
- In the checked-in config, impact analysis, API contract, test data, performance, and quality gate are enabled; cross-run failure intelligence is disabled.
- **Why use it:** Run a configured QE assessment in one place and review agent status, findings, and overall risk together; it currently produces a risk assessment but does not itself enforce a Jenkins release gate.
- **Run:** `npm run qe:orchestrator`; edit the config to enable, disable, or reorder agents.
- **Prerequisite / flow:** Every enabled `script` must exist in the root `package.json`; order agents so prerequisite reports are created before consumers such as the quality gate.

### Typical workflow

1. Prepare or update the requirements, API contracts, impact map, test data, and performance thresholds used by the agents.
2. Run focused agents as needed: impact analysis after code changes, API contract analysis after an API spec change, and performance intelligence after load tests.
3. Use test-data intelligence to check data/scenario coverage and generate synthetic records; use AI evaluation when changing an AI-powered QE workflow.
4. Run `npm run qe:orchestrator` to execute the agents enabled in its config and create a unified report.
5. Review the reports and warnings. A mapped-test recommendation or low risk score is evidence to guide decisions, not proof that unselected tests or unmeasured risks are safe.

## AI Util Files

### `utils/ai-test-design/qe-test-design-agent.ts`

- Reads requirements from `ai-utils/checkout-requirements.md` by default; the first command-line argument can select another input.
- Sends the requirements to the configured local Ollama model to design risk-based test scenarios.
- Validates the returned scenario structure, required fields, risk values, and unique scenario IDs.
- Records scenarios, requirement links, preconditions, steps, and expected results.
- Writes `ai-utils/qe-test-design.json` and `ai-utils/qe-test-design.md` by default; the second and third command-line arguments can change those output paths.
- **Prerequisite / flow:** Requires a requirements file and Ollama; feed the generated JSON to `qe-test-to-code.ts` to draft automation candidates.

### `utils/ai-test-design/qe-test-to-code.ts`

- Reads `ai-utils/qe-test-design.json` and selects scenarios marked as automation candidates.
- Asks the configured local Ollama model for a Playwright TypeScript callback body for each selected scenario.
- Wraps each body in a Playwright test with requirement, scenario, and risk annotations; unknown application details are reported rather than invented.
- Checks generated TypeScript syntax and notes missing details and implementation notes; this does not prove a test will run correctly.
- Writes candidate `.spec.ts` files to `ai-utils/generated-tests/` and a summary to `ai-utils/qe-test-generation-report.md`; it clears the generated-tests folder before generating new files.
- **Prerequisite / flow:** Run test design first and review candidates before adding or executing them; generated syntax passing does not prove locators or application behavior are correct.

### `utils/qe-failure-agent.ts`

- Reads Playwright JSON from `ai-utils/agent-results.json` by default; command-line arguments 1 and 2 select input and report paths.
- Collects failed, timed-out, and interrupted test results, including the test name, error, file, retry, and duration.
- Classifies errors with predefined patterns and assigns a priority with likely causes and investigation checks.
- Writes a Markdown report to `ai-utils/qe-failure-report.md` by default.
- Its diagnoses are rule-based suggestions, not confirmed root causes.
- **Prerequisite / flow:** Generate the Playwright JSON report first; this agent is deterministic and does not require Ollama.

### `utils/qe-failure-intelligence.ts`

- Reads the JSON Lines history at `ai-utils/qe-run-history.jsonl` by default; command-line arguments can select the input and output.
- Groups records by test and keeps the final retry for each run when comparing outcomes.
- Identifies patterns such as new, recurring, recovered, or intermittent failures.
- Scores currently failing tests to assign an investigation priority and rationale.
- Writes a cross-run Markdown report to `ai-utils/qe-failure-intelligence.md` by default.
- **Prerequisite / flow:** Run `qe:history` after Playwright runs; accumulated history is needed to identify cross-run patterns.

### `utils/qe-failure-triage.ts`

- Exports `triageFailure`, a reusable rule-based helper; it does not read files or write a report itself.
- Takes a `FailureEvidence` object (test details and error text) as input.
- Matches common signatures such as timeouts, assertions, accessibility errors, and locator failures.
- Returns a `TriageFinding` containing category, priority, observed evidence, hypotheses, and next actions.
- `qe-ai-analysis.ts` uses this helper to add deterministic triage alongside its AI analysis.

### `utils/qe-quality-gate.ts`

- Reads failure intelligence, test-design JSON, Playwright JSON, active requirements, and optional requirement-risk configuration.
- Uses `ai-utils/qe-failure-intelligence.md`, `ai-utils/qe-test-design.json`, `ai-utils/agent-results.json`, `ai-utils/checkout-requirements.md`, and `ai-utils/requirement-risks.json` by default.
- Links tests to requirements using `REQ-...` IDs in test titles or annotations, then checks scenario coverage, execution results, and risk.
- Produces a `PASS`, `REVIEW`, or `BLOCK` decision; high/critical requirements without passing test evidence block the gate.
- Writes `ai-utils/qe-release-readiness.json` and `ai-utils/qe-release-readiness.md`; `QE_GATE_*` environment variables configure inputs and gate behavior.
- **Prerequisite / flow:** Prepare requirements, test design, and Playwright reports; put `REQ-...` IDs in test titles or annotations so execution can map to requirements.

### `utils/qe-run-history.ts`

- Reads Playwright JSON from `ai-utils/agent-results.json` by default; command-line arguments 1 and 2 select input and history paths.
- Extracts completed test outcomes, including passed, failed, timed-out, interrupted, and skipped results.
- Adds a run ID, timestamp, commit, test identity, retry, duration, and normalized error signature to each record.
- Appends one JSON record per line to `ai-utils/qe-run-history.jsonl` by default, preserving records from earlier runs.
- The history can then be analyzed by `qe-failure-intelligence.ts`.
- **Prerequisite / flow:** Generate the Playwright JSON report first; CI run IDs are used to group retries and results from the same run.

### `utils/qe-triage-demo.ts`

- Defines two sample `FailureEvidence` objects: a timeout involving a disabled button and an accessibility-related assertion.
- Passes each example to `triageFailure` from `qe-failure-triage.ts`.
- Prints each result as formatted JSON in the terminal.
- Uses mock data only; it does not read a Playwright report or run tests.
- Run it with `npx tsx utils/qe-triage-demo.ts`.

### `utils/qe-ai-analysis.ts`

- Reads Playwright JSON from `ai-utils/agent-results.json` by default; command-line arguments 1 and 2 select input and output paths.
- Collects failed, timed-out, and interrupted results with errors, logs, project details, retries, and artifact paths.
- Adds deterministic findings from `qe-failure-triage.ts` and asks a local Ollama model for evidence-based causes and debugging steps.
- Writes a Markdown report to `qe-ai-failure-report.md` by default; set `OLLAMA_URL` or `OLLAMA_MODEL` to change the local model endpoint or model.
- AI output is advisory; if the model is unavailable, the report retains the failure evidence and triage and notes the AI-analysis error.
- **Prerequisite / flow:** Generate the Playwright JSON report first; deterministic triage is still included if Ollama cannot be reached.

## Playwright Code Reviewer

The code reviewer combines deterministic source checks with a local Ollama
review. It reviews code statically; it does not run Playwright tests or prove
that a reported concern is a runtime defect.

### What it checks

- Deterministic checks flag patterns such as `test.only()`, fixed
  `waitForTimeout()` delays, XPath and low-level selector use, forced actions,
  skipped tests, generic assertions, and `console.log()` calls.
- Ollama reviews the supplied code for evidence-backed concerns such as
  locator reliability, assertions, test isolation, maintainability, API
  validation, hardcoded values, async usage, and accessibility testing where
  relevant.
- AI findings are accepted only when their file, line, and evidence match the
  supplied source. The Markdown report includes severity, evidence, and
  recommendations. Its code quality score is a simple severity-weighted
  heuristic, not a calibrated quality metric.

### Current scan scope

Run the command from the repository root. At present, the configured scan
directory is `code-review-test/`, plus the root `playwright.config.ts` or
`playwright.config.js` if present. Other directories such as `tests/`,
`pages/`, and `fixtures/` are not currently scanned unless `SCAN_DIRS` is
updated in `qe-code-reviewer-agent/utils/qe-playwright-code-reviewer.ts`.

The scanner accepts TypeScript and JavaScript files, ignores generated and
hidden directories (including `node_modules`, `test-results`, and `RAG`), and
limits a review to 60 files, 35 KB per file, and 20,000 total source
characters. Files beyond these limits may be skipped.

### Setup and run

The AI portion requires a running local Ollama service. By default, the agent
uses `http://localhost:11434` and the `qwen3:4b` model. Set `OLLAMA_URL` or
`OLLAMA_MODEL` to override those defaults. Install the model if needed:

```sh
ollama pull qwen3:4b
```

Run the review with:

```sh
npm run qe:code-review
```

The command runs deterministic checks, sends the bounded source set to
Ollama, validates AI finding evidence against the scanned files, and writes:

- `qe-code-reviewer-agent/test-results/qe-code-review/qe-playwright-code-review.md`
- `qe-code-reviewer-agent/test-results/qe-code-review/qe-playwright-code-review.json`

Review the findings and source code before making changes. Both static and AI
findings are advisory; the report does not execute tests, and its score should
not be treated as a release gate.
